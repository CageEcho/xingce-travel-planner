# 知识库数据规范
## 高端旅行智能方案生成平台「行策」

| 项 | 内容 |
| --- | --- |
| 文档类型 | 数据规范（字段标准 / 标签体系 / 来源标注 / 更新与校验机制） |
| 版本 | v1.0 |
| 日期 | 2026-10-25 |
| 唯一来源 | 口径：`seed/taxonomy.py`；表结构：`backend/app/models/resource.py`；验收：`seed/generate.py::assert_catalog` |
| 数据声明 | **全部为演示用模拟数据**（`is_synthetic=true`）：酒店、餐厅、供应商为虚构名称，景点为真实公共地标，历史方案为脱敏模拟。不代表真实库存、价格或可售状态 |

---

## 1. 为什么要有这份规范

资源信息原来散在多张表格和顾问个人经验里，会带来三个问题：

- 同一个字段各写各的，比如「儿童可住」有人写「可」，有人写「6 岁以上」，系统没法统一判断；
- 不知道信息从哪来、多久没更新，过期了还在用；
- 空着的字段被当成「没限制」，这是最危险的一种错。

这份规范要解决的就是三件事：**字段统一、来源可追溯、过期可发现**。知识库同时服务两个下游：RAG 召回（Dify 知识库、候选池摘要），以及确定性约束校验（H1–H12）。

## 2. 类目与规模

| 类目 | 表 | 主键规则 | 条数 | 说明 |
| --- | --- | --- | --- | --- |
| 供应商 | `supplier` | `SUP-001` | 45 | 含类目（酒店集团 / 旅馆联盟 / 地接 / 用车 / 餐饮 / 票务）、合同到期日 |
| 酒店 | `hotel` | `HTL-{城市}-0001`，陷阱资源 `HTL-{城市}-T1-001` | 300 | 东京 130 / 京都 115 / 箱根 55 |
| 房型 | `room_type` | `RM-{酒店ID后缀}-{序号}` | 909 | 容量、儿童年龄、加床政策 |
| 餐厅 | `restaurant` | `RST-{城市}-001` | 180 | 每城 60 家 |
| 景点 | `poi` | `POI-{城市}-001` | 75 | 真实地标 + 真实坐标 |
| 用车 | `vehicle` | `VEH-{城市}-001` | 30 | 含无障碍福祉车 |
| 门票 | `ticket` | `TKT-{城市}-001` | 111 | 普通 / 按时段预约 / 快速通道 / 特别参观 / 导览 / 通票 |
| 路线 | `route` | `RTE-{城市}-01` | 39 | 按主题聚合、地理就近排序的景点序列 |
| 历史方案 | `history_plan` | `HIS-{yyyymm}-001` | 80 | 客群画像、所用资源、成交结果、返工轮次、Bad Case 归因 |
| **合计** | | | **1,769** | 另有价格档 `rate_plan` 3,043 条 |
| 标签字典 | `tag_dict` | 标签英文键 | 113 | 标签体系，见 §4 |

**城市代码**：东京 `TYO`、京都 `KYO`、箱根 `HKN`。

**价格只放在 `rate_plan` 表里。**资料表（门票、路线、历史方案等）不放任何价格字段，由验收项 C9 强制检查。模型不报价，所有金额都由规则引擎从价格档计算。

## 3. 字段标准

### 3.1 空值语义（最重要的一条）

**NULL 表示「未记录」，不等于「无限制」。**

| 字段 | 空值的含义 | 约束层判定 |
| --- | --- | --- |
| `room_type.min_child_age` | 儿童年龄政策没问到 | 有儿童时 H1 → 待核实 |
| `restaurant.closed_days` / `poi.closed_days` | 休息日没记录 | H3 → 待核实 |
| `restaurant.dietary_support = []` | 是否支持饮食限制没问到 | 客户有忌口时 H2 → 待核实，检索阶段降权 |
| `restaurant.child_friendly` | 没记录 | 不作为排除依据 |
| `poi.accessible` | 无障碍情况没记录 | 有轮椅需求时 H9 → 待核实 |
| `vehicle.luggage_28` | 行李容量没记录 | H4 → 待核实 |

### 3.2 枚举字段

| 字段 | 取值 |
| --- | --- |
| `hotel.tier` | `4star` 四星 / `5star` 五星 / `luxury` 奢华 / `ryokan` 高端旅馆 / `boutique` 精品 |
| `restaurant.price_band` | `budget` / `mid` / `high` / `luxury` |
| `restaurant.dietary_support` | `no_raw` 忌生食 / `vegetarian` / `vegan` / `halal` / `no_pork` / `gluten_free` |
| `poi.intensity` | `easy` / `moderate` / `hard` |
| `ticket.ticket_type` | `general` / `timed_entry`（必须按时段预约）/ `priority` / `special_visit` / `guided_tour` / `pass` |
| `route.duration_type` | `half_day`（≤4 小时，含交通）/ `full_day`（≤8 小时） |
| `history_plan.outcome` | 成交 / 修改后成交 / 未成交 |
| `history_plan.bad_case_tags` | 知识缺失 / 检索偏差 / 行程冲突 |

### 3.3 星期与时间

- `closed_days` 用 0–6 表示，**0 = 周日**，和 PostgreSQL 的 `EXTRACT(DOW)` 一致；Python 的 `weekday()` 是 0 = 周一，换算统一走 `constraints.dow()`。
- 坐标必填（铁律①），通勤估算按「直线距离 × 1.35 路网系数 ÷ 城市均速」计算。

## 4. 标签体系

标签分 8 组，共 113 个，每个标签都必须在 `tag_dict` 里登记（验收项 C5）：

| 分组 | 示例 | 用途 |
| --- | --- | --- |
| 设施 | 家庭房、连通房、儿童俱乐部、私汤、包间 | 硬过滤与排序（如多人家庭优先连通房） |
| 风格 | 安静、设计感、历史建筑、京町家 | 偏好匹配 |
| 客群 | 性价比、商务、亲子友好、长辈友好、无障碍线路 | 客群匹配、路线推荐 |
| 餐饮 | 怀石料理、主厨发办、米其林、营业到深夜 | 餐饮偏好 |
| 场景 | 河景、夜游、雨天可去、宜早去 | 天气与时段安排 |
| 体验 | 艺术、动物、火车、动漫、神社、温泉巡游 | 兴趣命中（规则编排与评测都按它判断） |
| 区位 | 市中心、近新干线 | 首晚 / 末晚住宿选择 |
| 约束提示 | 人多、需预约、需一整天 | 提醒顾问 |

新增标签的流程：先在 `seed/taxonomy.py` 登记中文名、分组和适用类目，再在数据里使用；不登记的话，生成器的验收会失败。

## 5. 来源标注与校验状态

### 5.1 每条资源必带的治理字段

| 字段 | 含义 |
| --- | --- |
| `source_type` | 来源类型（见下表） |
| `source_ref` | 具体出处，如「SUP-003 2026–27 年度合同/报价单」「ADV-04 实地踩线记录（2026-08-20）」 |
| `verified_status` | `verified` 已人工校验 / `pending` 待校验 / `expired` 复核过期 |
| `verified_by` / `verified_at` | 校验人（顾问编号，已脱敏）与校验日期 |
| `review_due` | 下次复核到期日；待校验的资源这里填校验截止日 |

| 来源类型 | 可信度 | 典型内容 |
| --- | --- | --- |
| `supplier_contract` 供应商合同 / 报价单 | 高 | 房型、容量、政策 |
| `official_site` 官方网站 / 公告 | 高 | 景点开放时间、门票规则 |
| `advisor_visit` 顾问实地踩线 | 高（主观项要交叉验证） | 顾问备注、无障碍实况、餐厅体验 |
| `historical_order` 历史订单回填 | 中 | 从过往订单反推的信息 |
| `ota_reference` OTA 公开信息 | 低，仅供参考 | 新资源首次录入 |

### 5.2 复核周期（更新机制）

| 类目 | 周期 | 理由 |
| --- | --- | --- |
| 餐厅、门票 | 90 天 | 营业时间、预约规则变化快 |
| 酒店、景点、路线 | 180 天 | 相对稳定 |
| 用车 | 365 天 | 车型与装载基本不变 |

**状态流转**：

```
新录入 ──→ pending（待校验，有截止日）──人工核对──→ verified（review_due = 校验日 + 周期）
                                                     │
                                       到期未复核 ──→ expired ──重新核对──→ verified
```

### 5.3 治理状态如何进入生成链路

| 状态 | 检索 | 约束校验 | 前端 |
| --- | --- | --- | --- |
| `verified` | 正常进入候选池 | 无影响 | 溯源浮层显示「来源 · 已校验 日期，下次复核 日期」 |
| `pending` | 进入候选池 | **H12 → 待核实**，写进待核实清单 | 显示「待人工校验（截止日期）」 |
| `expired` | **直接排除，不进候选池** | 万一出现则 H12 → 阻断 | — |

此外，必须按时段预约的门票（`timed_entry`）在方案用到对应景点时，会自动写进待核实清单（code = `TKT`），客户版放在「预订前确认」的第一位。

## 6. 验收与巡检

### 6.1 入库前验收（`seed/generate.py`，不通过就拒绝入库）

| 编号 | 验收项 |
| --- | --- |
| T1–T12 | 12 类约束陷阱都存在（保证约束校验有真实的拦截对象） |
| C1 | 酒店 300 家 |
| C2 | 供应商 ≥ 40 家 |
| C3 | 结构化资料 ≥ 1,500 条（不含价格档） |
| C4 | 七大类目齐全：酒店 / 房型 / 车辆 / 餐厅 / 门票 / 路线 / 历史方案 |
| C5 | 资源上出现的每个标签都已在标签字典登记 |
| C6 | 每条资源都有来源标注和校验状态，已校验的必须有校验人和日期 |
| C7 | 「复核过期」状态与到期日一致 |
| C8 | 外键完整：房型→酒店、门票→景点、路线→景点、历史方案→酒店/路线、资源→供应商 |
| C9 | 价格只存在于价格档表 |

当前结果：**21/21 通过**。`backend/tests/test_catalog.py` 也覆盖了这些验收项。

### 6.2 定期巡检（`python seed/quality_report.py`）

巡检会输出各类目规模、校验状态分布、30 天内到期的复核项、来源分布和关键字段空值率。最新结果见 [`seed/quality_report.md`](../seed/quality_report.md)，摘录如下：

| 类目 | 已校验占比 | 待校验 | 复核过期 | 30 天内到期 |
| --- | --- | --- | --- | --- |
| 酒店 | 88.7% | 22 | 12 | 32 |
| 餐厅 | 87.8% | 13 | 9 | 32 |
| 用车 | 83.3% | 2 | 3 | 0 |
| 景点 / 门票 / 路线 | 100% | 0 | 0 | 0 |

关键字段空值率最高的是「餐厅可满足饮食限制」（20.6% 未记录），也就是说，顾问补录工作应该优先从这一项开始。

## 7. 与 Dify 知识库的同步

`python dify/build_knowledge.py` 会把种子数据转换成 14 份 Markdown 文档：酒店和餐厅按城市拆分，景点、用车、门票、路线、历史方案各一份，另有 SOP、攻略和案例库。每条资源写成一个分段，分段里带资源 ID、结构化字段和「来源 · 校验状态 · 下次复核」，**不带价格**。标签中文名和来源口径与本规范同出一源（`seed/taxonomy.py`），避免两边的写法不一致。
