## 1. 一句话

**把高端定制旅行顾问「查资源 + 拼行程 + 算成本 + 出方案书」这段纯信息工作，变成一条可追溯、可核验、可交付的软件链路**，让顾问只做需要人判断的部分。

---

## 2. 为什么做（问题）

### 2.1 现状链路与耗时分布

~~~
客户微信一段话
   ↓ 反复追问（信息常常问不全，做到一半才发现漏了预算口径/忌口）
需求靠顾问记在脑子里
   ↓ 翻 PDF / 问同行 / 查群聊记录（资料散在 6 个渠道）
手工拼行程（避坑全靠经验）
   ↓ Excel 手算成本
Word 排版方案书
   ↓ 客户改一句，上面几步重来
~~~

### 2.2 三个要命的问题

| # | 问题 | 业务后果 |
| --- | --- | --- |
| P1 | **需求采集不完整**：忌口、无障碍、预算是否含机票，常常漏问 | 方案做完才发现前提错了，整单返工 |
| P2 | **资源知识不可复用**：「哪家旅馆不接 6 岁以下」只在老顾问脑子里 | 新人无法独立出稿；老人离职即资产流失；同一个坑反复踩 |
| P3 | **交付物纯手工**：逐单排版、手算成本 | 首稿周期长；算错价直接吃掉利润 |

### 2.3 为什么现在做

- 模型的**结构化输出 + 长上下文**已经稳定到可以做「抽取与编排」，但**仍不可信其事实**——这个「能用但不可全信」的状态，正好是「模型 + 规则引擎」混合架构的窗口期；
- 通用 AI 行程工具都停在 C 端灵感层，**没有人解决对客交付这一关**（无净价、无库存口径、无约束校验）；
- 需求侧向定制与高客单倾斜（见行业报告 §2），顾问产能是瓶颈。

## 3. 值不值得做（收益测算）

> ⚠️ **本节全部是待验证的估算，不是实测结果。** 所有参数取自一线定性观察，验证方法见 §7。产品决策不建立在这些数字的精确值上，只建立在**方向**上。

### 3.1 单方案工时模型（假设）

| 环节 | 现状工时（假设） | 引入后（假设） | 依据 |
| --- | --- | --- | --- |
| 需求澄清 | 1.5 h | 0.8 h | AI 抽取 + 结构化追问，人做确认 |
| 资源检索与核对 | 3.0 h | 0.5 h | 结构化硬过滤，确定性问题 |
| 行程编排 | 2.0 h | 1.0 h | 模型编排 + 规则校验 + 自动重排，人做微调 |
| 成本核算与出稿 | 1.5 h | 0.2 h | 规则引擎 + 模板渲染 |
| **合计** | **8.0 h** | **2.5 h** | —— |

**若假设成立**：单方案净投入下降约 2/3，顾问产能理论上提升 2–3 倍。

**但这个数字必须先被证伪**：H1（检索是否真的是最大占用项）不成立，整个优先级就要重排 —— 见 PRD-v2 §4.4 的 H1–H5。

**外部佐证（见 [竞品分析 §5.1](09-竞品分析.md)）**：行业公开报道中，一份定制方案「经反复沟通、修改、敲定至少历时三四天」，部分高端机构「单订单平均沟通时长超 30 小时」。相较之下，本表假设的 8 小时/方案属**保守估计**。

**但同一批资料也暴露了我们没考虑到的一点**：有从业者称平台定制需求单的**成单率最高约 10%**——意味着顾问约九成的方案工时是**沉没成本**。若该比例属实，产品的收益不只是「单方案省 5.5 小时」，而是「让沉没的那九成变得更便宜」。这一条已补入 §7 的验证清单。

### 3.2 不只是效率

| 收益类型 | 说明 | 可衡量性 |
| --- | --- | --- |
| 效率 | 单方案工时下降、首稿周期缩短 | 工时日志 / CRM 时间戳 |
| **质量** | 硬约束零违反，避免「周一闭馆」「房型住不下」这类对客事故 | **可直接计数**（硬约束拦截数） |
| **资产化** | 顾问经验沉淀为资源库与约束规则 | 结构化率、规则条数 |
| 新人培养 | 新人靠系统即可出结构正确的首稿 | 新人独立出稿周期 |

> 💡 真正值钱的不是省下的 5.5 小时，而是**把「老顾问的脑子」变成可查询、可校验、可回归测试的资产**。效率是结果，资产化是原因。

### 3.3 成本

| 项 | M0 投入 |
| --- | --- |
| 人力 | 1 人（产品 + 研发一体），约 3 周 |
| 模型 | DeepSeek / Claude，单次生成实测 ≈ 2.4k output tokens、约 19.5 s（见[评测报告](10-评测标准与评测报告.md)），量级可忽略 |
| 基础设施 | 本地 PostgreSQL 16 / 内嵌 PG，无云开销 |
| 数据 | M0 用合成演示数据（769 条资源记录），**真实数据治理成本是二期的主要投入** |

## 4. 做什么（范围）

### 4.1 M0 做什么

| 做 | 不做 |
| --- | --- |
| 自然语言需求采集 + 多轮引导 + 结构化需求卡 | 语音输入、多语言 |
| 顾问人工确认卡点 | 客户侧自助入口 |
| 资源硬过滤 + 候选池 | 语义检索 / 向量召回（M1） |
| 模型编排 + 三道防线 + 约束校验 + 自动重排 | 多方案 A/B、跨国联程 |
| 规则引擎成本核算 | 佣金分成、财务对账 |
| 客户版方案预览 + PDF / 长图导出 | 在线预订、库存锁定、电子签 |
| 3 城（东京/京都/箱根）合成数据 | 全量城市、真实供应商库存 |

### 4.2 三个里程碑

| 里程碑 | 内容 | 判定 |
| --- | --- | --- |
| **M0** | 最小可跑闭环：原话 → 需求卡 → 生成 → 校验 → 成本 → 交付 | G1–G5 五条门槛（§6） |
| **M1** | 加语义检索（pgvector 双路召回 + RRF 融合） | 召回质量指标 |
| **M2** | 加编辑能力（锁定 + 增量重排 + 版本对比） | 顾问修改率下降 |

### 4.3 明确不做（防范围蔓延）

顺手做预订、做 CRM、做财务、做客户端小程序 —— 任何一项都会让 M0 延期，且都有成熟玩家。**范围表即变更基线，超出需走变更评审。**

## 5. 怎么做（方案要点）

三条架构级决策，全部写死在代码里，不靠提示词约束：

| 决策 | 内容 | 为什么是架构级 |
| --- | --- | --- |
| **D-A** | **价格与事实字段绝不进入模型生成路径**：模型只输出 `resource_id`，金额由 Python 规则引擎算 | 提示词会被绕过，架构隔离不会 |
| **D-B** | **三道防线**：① 模型只选 ID → ② 服务端校验 ID 在候选池内 → ③ 回填库内事实并二次比对字段 | 防线 ② 拦截「ID 看着合理但不在候选池」的编造 |
| **D-C** | **三态校验 PASS / FAIL / UNKNOWN**：缺数据不算通过，显式暴露为待核实项 | 二值判定会让缺字段静默变成「通过」，这是最难发现的故障 |

技术栈与实现细节见 [技术适配声明与第一阶段技术开发文档](技术适配声明与第一阶段技术开发文档.md)。

## 6. 上线门槛（一票否决）

| # | 门槛 | 判定方式 |
| --- | --- | --- |
| **G1** | 硬约束在测试集中**零违反** | 评测集自动跑测，blocking violations = 0 |
| **G2** | 事实字段**无编造**，100% 可溯源到 `resource_id` | 引用校验 + 一致性回查 |
| **G3** | 成本核算与手工核算**逐项一致** | 多份方案对比，误差为 0 |
| **G4** | 人工确认卡点**有效**：未确认不得生成/导出 | 接口层校验，非仅前端 |
| **G5** | 净价权限**隔离有效** | 服务端剥离，非前端隐藏 |

**这五条不满足，不得对客使用。** M0 实测结果见 [数据分析报告](08-数据分析报告.md)。

## 7. 怎么验证（立项后第一件事）

> 立项后的第一项工作不是写代码，是**测手工基线**。没有基线，后面无法证明任何价值。

| 假设 | 验证方法 | 若不成立 |
| --- | --- | --- |
| H1 检索是最大工时占用项 | 4 名顾问 × 2 周工时日志，30 分钟粒度 | 产品重心移向编排辅助 |
| H2 返工主因是需求采集不完整 | 抽近 6 个月方案，标注修改原因分类 | 重心移向增量重排与版本管理 |
| H3 新人与资深差距源于资源熟悉度 | 两组顾问工时分项对比 | 需要的是路线模板而非检索 |
| H4 顾问接受门槛是可追溯性 | 原型可用性测试，带/不带来源标注两版 | 先提生成质量再谈可解释性 |
| H5 现有资料结构化程度不足以支撑硬过滤 | 抽样统计关键字段结构化率 | 可跳过数据治理直接做检索 |
| **H6 未成交方案的工时占比很高（沉没成本）** | 统计询单量 / 成交量与各自的方案工时 | 若成单率高，收益测算应回到「单方案提效」口径 |

**H5 最关键**：若成立，数据治理必须是第一里程碑而非并行任务，排期要改。

## 8. 风险与对策

| # | 风险 | 影响 | 对策 |
| --- | --- | --- | --- |
| R1 | 知识库冷启动数据质量不足 | 检索召回差 → 顾问不信任 → 产品失败 | 先窄后宽（3 城）；数据就绪设为第一里程碑 |
| R2 | 关键属性未结构化导致硬过滤静默失效 | 最难发现的故障 | 三态校验；字段完整度看板 |
| R3 | 顾问不愿维护数据 | 库越用越旧 | 维护动作嵌入日常流程（成交回流、Badcase 自动生成补录工单） |
| R4 | 模型编造价格/房态 | 对客事故，商誉损失 | 三道防线（D-B） |
| R5 | 顾问觉得「改比重做还慢」 | 弃用 | 锁定 + 增量重排列为 M2 P0 |
| R6 | 缺少基线导致无法证明价值 | 无法争取后续投入 | 开发前先测基线（§7） |
| R7 | 数据合规（PII） | 合规风险 | 入库与送模型前脱敏 |

## 9. 结论与申请

**建议立项，按 M0 → M1 → M2 分段投入，每段设门槛，不通过不继续。**

申请：
1. M0 资源：1 人 3 周 + 模型额度；
2. 并行启动 §7 的基线测量（这部分需要业务方配合，不占研发资源）；
3. M0 结束后以 §6 的 G1–G5 与实测数据（[数据分析报告](08-数据分析报告.md)）作为是否进入 M1 的评审依据。
