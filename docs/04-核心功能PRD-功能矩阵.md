| ID | 功能 | 描述 | 优先级 | 状态 | 验收标准 | 实现 |
| --- | --- | --- | --- | --- | --- | --- |
| F2-1 | 硬过滤 | 城市 / 日期可售 / 房型容量 / 儿童政策 / 档次 / 饮食 / 无障碍 / 车辆装载 | P0 | ✅ | 不符合条件的资源不得进入候选池 | `services/retrieval.py` |
| F2-2 | 候选池构建 | 按天按类型组织候选 | P0 | ✅ | 生成阶段只能引用池内资源 | `retrieval.build_pool` |
| F2-3 | 候选不足保护 | 池内 < 3 时不硬生成 | P0 | ✅ | 返回 `CANDIDATES_TOO_FEW` + 结构化建议 | `MIN_CANDIDATES_TO_PLAN=3` |
| F2-4 | 排序 | 标签 0.50 / 价格 0.30 / 时效 0.20 / 商业 0.00 | P1 | ✅ | 权重可配置 | `core/config.py` |
| F2-5 | **商业权重上限锁死** | 商业优先级权重 > 0.10 直接启动失败 | P0 | ✅ | 配置校验器抛错 | `config.cap_commercial` |

| F2-7 | 语义检索（双路召回 + RRF） | —— | P2 | ⛔ | M1 范围 | —— |

**为什么硬过滤优先于向量召回**：向量召回能找到「相似的」，但找不到「可用的」。一间住不下 3 个人的房，语义上再匹配也是错的。

## 4. F3 · 行程生成与防幻觉 ⭐

| ID | 功能 | 描述 | 优先级 | 状态 | 验收标准 | 实现 |
| --- | --- | --- | --- | --- | --- | --- |
| F3-1 | 日程骨架 | 按城市与天数生成骨架与转场日 | P0 | ✅ | 转场日识别正确 | `planner.build_day_skeleton` |
| F3-2 | 约束简报 | 把需求卡与上轮违规转成模型可读简报 | P0 | ✅ | 重排轮次能看到上轮问题 | `planner.build_constraint_brief` |
| F3-3 | LLM 编排 | 模型**只输出 resource_id**，不输出事实与价格 | P0 | ✅ | 输出中不含任何价格字段 | `planner.plan_itinerary_llm` |
| F3-4 | **防线① Schema 约束** | JSON Schema 强约束输出结构 | P0 | ✅ | 结构不合法 → 重试 → `LLM_INVALID_OUTPUT` | `schemas/plan.py` |
| F3-5 | **防线② 引用校验** | 逐个检查 ID 是否在本次候选池内 | P0 | ✅ | 池外 ID 100% 被拦截并计数 | `render.py` 引用校验 |
| F3-6 | **防线③ 事实回填与比对** | 用 DB 真实字段覆盖模型输出并二次比对 | P0 | ✅ | 名称/容量/时间/价格与库一致 | `render.render_plan`、`_consistency` |
| F3-7 | 自动重排 | 存在阻断项时带上轮违规重新编排，≤ 3 轮 | P0 | ✅ | 重排轮次可见 | `generate_with_validation` |
| F3-8 | 确定性编排器 | 无模型/降级时的规则编排 | P0 | ✅ | `PLANNER_MODE=heuristic` 可跑通全链路 | `planner.plan_itinerary_heuristic` |

**防线② 为什么必要**：模型完全可能输出一个格式正确、看起来像真的 `HTL-KYO-T1-007`，但它不在本次候选池里（可能不存在，也可能已被硬过滤掉）。防线 ① 拦不住这个，防线 ③ 回填时才会炸——所以必须有 ②。

| F4-5 | H5 通勤时长 | ≤ 180 分钟（转场日 300） | P0 | ✅ | 条目缺经纬度 |
| F4-6 | H8 可售性 | 日期区间有可用价格档 | P0 | ✅ | 无价格记录 |
| F4-7 | H11 价格时效 | 合约价且 90 天内 | P0 | ✅ | 无记录 / 其它来源 |
| F4-8 | **三态判定** | PASS / FAIL（阻断） / UNKNOWN（待核实） | P0 | ✅ | —— |
| F4-9 | 待核实清单 | 所有 UNKNOWN 汇总为人工核对清单 | P0 | ✅ | —— |

**三态是这个模块的全部意义**：二值判定会把「没有数据」静默变成「通过」，而这是最难发现、后果最严重的故障（PRD-v2 风险 R2）。

## 12. 明确不做（范围基线）

| 项 | 原因 |
| --- | --- |
| 在线预订 / 库存锁定 | 重资产，需供应商直连；本产品定位是**方案生成**不是库存查询 |
| CRM / 客户档案 | 已有成熟玩家，应做对接而非自建 |
| 财务对账 / 开票 / 佣金分成 | 与核心价值无关 |
| C 端自助规划 | 与产品前提（顾问把关）冲突 |
| 机票 / 邮轮 / 签证代办 | M0 范围外 |

**任何超出本表的需求需走变更评审**，这是防止范围蔓延（风险 R7）的唯一手段。
