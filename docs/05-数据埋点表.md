## 1. 设计原则

1. **先定指标，再定埋点**。每个事件必须能回答第 6 节里的某个具体问题；回答不了任何问题的事件不埋。
2. **一个事件一件事**，属性描述上下文，不用一个 `action` 字段塞所有行为。
3. **不埋原话**。客户原文只上报长度与 SHA-256 digest（前 16 位），与后端 `logging.digest()` 口径一致。
4. **服务端优先**。凡是服务端知道的（校验拦截数、token、重排轮次）一律服务端埋，前端只埋「人做了什么」。
5. **可对齐**。前后端共用 `conv_id` / `plan_id` / `card_version` 做串联。

---

## 2. 命名规范

~~~
<域>_<对象>_<动作>      例：intake_message_submit、plan_generate_done、proposal_export
~~~

| 域 | 含义 |
| --- | --- |
| `intake` | 需求采集 |
| `card` | 需求卡 |
| `plan` | 生成与校验 |
| `proposal` | 客户版与交付 |
| `sys` | 可靠性与错误 |

事件名与属性名一律 **snake_case**；布尔属性以 `is_` / `has_` 开头；时长统一 `_ms`，金额统一 `_cny` 并为整数分。

## 3. 公共属性（所有事件必带）

| 属性 | 类型 | 说明 | 来源 |
| --- | --- | --- | --- |
| `event_id` | string | UUID，幂等去重 | 客户端生成 |
| `event_time` | int | 毫秒时间戳 | 上报端 |
| `user_id` | string | 顾问 ID | 鉴权 principal |
| `role` | enum | sales / advisor / supervisor / procurement / admin | 鉴权 principal |
| `conv_id` | string | 会话 ID（可空） | 上下文 |
| `plan_id` | string | 方案 ID（可空） | 上下文 |
| `client` | enum | web / api | 上报端 |
| `app_version` | string | 前端构建版本 / 后端 git sha | 构建注入 |
| `env` | enum | local / staging / prod | 配置 |

## 5. 隐私红线（不可协商）

| 禁止上报 | 替代方案 |
| --- | --- |
| 客户原话全文 | `text_len` + `text_digest`（SHA-256 前 16 位） |
| 姓名 / 电话 / 邮箱 / 微信 / 证件号 / 地址 | 一律不进事件；脱敏在入库前完成 |
| API Key / 模型密钥 | 任何字段都不得包含 |
| **净价 / 成本价 / 价格档 ID** | 只上报对客总价 `total_cny`；成本类指标单独走内部看板并做角色隔离 |

> 埋点是最容易泄露 PII 的地方——业务代码有人review，埋点字段常常没人看。所以红线写在这里，并要求**新增埋点字段必须在 PR 描述中说明是否触及本表**。

## 6. 指标口径

| 指标 | 口径 | 依赖事件 | 目标方向 |
| --- | --- | --- | --- |
| 需求卡完整度 | `card_confirm.completeness` 均值 | card_confirm | ↑ |
| 平均追问轮次 | `card_confirm.rounds_total` 均值 | card_confirm | ↓（但不能牺牲准确） |
| 需求采集耗时 | 首条 `intake_message_submit` → `card_confirm` | 两者 | ↓ |
| **首稿生成时长** | `plan_generate_done.total_latency_ms` P50 / P90 | plan_generate_done | ↓ |
| **一次通过率** | `rounds = 1 且 blocking_final = 0` 占比 | plan_generate_done | ↑ |
| **硬约束拦截数** | `plan_violation.verdict = FAIL` 计数 | plan_violation | 观测（非 0 才说明防线在工作） |
| **引用校验拦截数** | `plan_refcheck_blocked.blocked_ids_count` 求和 | plan_refcheck_blocked | 观测 |
| 待核实项占比 | `unknown_count / 总条目数` | plan_generate_done | ↓ |
| **顾问修改率** | `plan_item_edit` 条目数 / 方案总条目数 | plan_item_edit | ↓ |
| 抽取纠错率 | `card_slot_edit.was_inferred = true` 占抽取槽位数 | card_slot_edit | ↓ |
| 交付完成率 | `proposal_export.success` 会话数 / `card_confirm` 会话数 | 两者 | ↑ |
| 单方案模型成本 | `plan_llm_call` token 求和 × 单价 | plan_llm_call | 观测 |
| 失败率 | `plan_generate_failed` / `plan_generate_start` | 两者 | ↓ |

> **最该看的两个**：**顾问修改率**（生成质量的最佳代理）与**硬约束拦截数**（证明约束层不是摆设）。
> 需要提醒的是：**硬约束拦截数不是越低越好**。它为 0 有两种可能——生成质量极高，或者校验根本没跑。必须结合评测集交叉验证。

## 7. 落地方案

### 7.1 现状

后端 `trace_log` 表已记录：`conv_id` / `plan_id` / `step` / `latency_ms` / `input_tokens` / `output_tokens` / `payload`，写入点在 `core/logging.py:write_trace`，边界是**不记密钥、客户原话只存 digest**。

对照本表，服务端已有约 40% 的事件覆盖（以 `step` + `payload` 的形式），但**字段未标准化**，无法直接聚合。

### 7.2 三步落地

| 步骤 | 内容 | 工作量估算 |
| --- | --- | --- |
| S1 | 把 `trace_log.payload` 按本表字段标准化，补 `event_name` 与公共属性列 | 0.5 天（后端） |
| S2 | 前端加轻量埋点 SDK（批量上报 `POST /api/v1/events`），覆盖 `intake` / `card` / `proposal` 域 | 1 天（前后端） |
| S3 | 指标聚合视图（SQL view 或物化表）+ 简易看板页 | 1 天 |

### 7.3 验收

- 跑一次完整闭环（原话 → 确认 → 生成 → 导出），事件序列完整且 `conv_id` / `plan_id` 可串联；
- 抽查 20 条事件，无任何 PII 与净价字段；
- 第 6 节的每个指标都能用一条 SQL 算出来——**算不出来的指标就是没定义清楚**。
