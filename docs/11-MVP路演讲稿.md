## 1. 三十秒版（电梯 / 自我介绍收尾）

> 高端定制旅行的顾问，做一份方案要花大半天：翻 PDF 查资源、手工拼行程、Excel 算成本、Word 排版。
> 市面上的 AI 行程工具都做不了这件事——**它们敢给旅行者看灵感，不敢给付了三十万的客户发方案**，因为会编酒店、编价格、推荐周一闭馆的美术馆。
>
> 我做的「行策」，是一条**给顾问用的、可核验的**方案生成链路：**模型只负责选资源 ID 和排顺序，所有价格和事实字段由规则引擎从数据库算出来，模型碰都碰不到**。
> M0 已经跑通端到端闭环，20 条评测用例、两种模式共 40 次跑测，**硬约束零违反**；一次生成约 24 秒。

**留钩子的收尾**：「这个项目我最想讲的不是它做了什么，是它**明确没做什么**——比如我没写用户调研报告，因为我没有真实访谈数据，写了就是编。」

## 2. 两分钟版（项目介绍标准答案）

**① 问题（20 秒）**

高端定制旅行单价十万到百万，但生产方式还停留在微信加 Word。顾问一份方案的工时，我的假设模型是 8 小时（[立项 §3.1](02-立项报告.md)，**这是假设不是实测**）；行业公开报道里有「一份定制方案反复沟通修改至少三四天」「单订单平均沟通时长超 30 小时」的说法（[竞品 §5.1](09-竞品分析.md)），所以 8 小时属于保守估计。

真正要命的是三件事：**需求问不全**（做到一半发现没问忌口，整单返工）、**经验不可复用**（「哪家旅馆不接 6 岁以下」只在老顾问脑子里）、**交付纯手工**（算错价直接吃掉利润）。

**② 为什么现在做、为什么别人没做成（30 秒）**

模型的结构化输出已经够稳，但**事实仍不可信**。这个「能用但不可全信」的状态，恰好是「模型 + 规则引擎」混合架构的窗口期。

- 通用 AI 行程工具（Mindtrip、Layla）停在 C 端灵感层，没有协议价、没有约束校验；
- OTA 的 AI 助手（携程问道、飞猪帮帮）**目标函数是转化不是正确**，而且私域协议价进不了平台库；
- B 端定制师工作台（路书云 TOS）管编排不管事实，官方口径是「80% 人工 + 20% 智能」。

**没有人解决「对客交付」这一关**，而这一关的门槛不是模型能力，是产品设计。

**③ 怎么做（50 秒）——核心只讲三条**

| 决策 | 一句话 | 为什么这么设计 |
| --- | --- | --- |
| **价格不过模型** | 模型只输出 `resource_id`，金额全部由 Python 规则引擎从库里算 | 提示词会被绕过，架构隔离不会 |
| **三道防线** | ① JSON Schema 约束输出 → ② 服务端校验 ID 确实在本次候选池内 → ③ 用库内真实字段回填并二次比对 | 防线 ② 专门拦「ID 长得很像真的，但根本不在池里」 |
| **三态校验** | PASS / FAIL / **UNKNOWN**，缺数据不算通过，显式列进「待核实清单」 | 二值判定会让缺字段静默变成「通过」，这是最难发现的故障 |

硬约束一共 7 条（房型容量、饮食禁忌、休馆日、车辆装载、单日通勤 ≤180 分钟、日期可售、价格时效 90 天），违反就自动带着上一轮的违规信息重排，最多 3 轮。

**④ 结果（20 秒）**

- 20 条评测用例 × 2 种模式 = 40 次跑测，**阻断性违规 0**（[评测 §6](10-评测标准与评测报告.md)）；
- 硬约束陷阱族 **8/8**，这些坑是我在种子数据里**故意埋的**（住不下 3 人的房型、限龄旅馆、过期合约价）；
- 自动重排 **4/20 触发，最多 2 轮全部收敛**，没有一条撞上 3 轮上限；
- 端到端一次生成 **约 24 秒**，模型输出的理由字段里**含数字的条数为 0**——这是验证「金额绝不经模型」的主动检查项。

## 3. 八分钟版（深聊 / 终面）

> 结构：问题 → 判断 → 架构 → 证据 → 缺口 → 下一步。**第五段是加分项，不要跳过。**

### 3.1 我怎么选的这条赛道（1 分钟）

我不用市场规模论证立项——3400 亿这种数字既无法验证也无法指导决策（[行业 §2.3](01-行业垂类分析报告.md)）。我看的是三条结构性结论：

1. 客单价极高（一单十万到百万），所以效率提升哪怕 30%，绝对收益也可观；
2. 生产过程是**纯信息工作**，理论上可被软件吃掉；
3. **错误成本极高**——推荐一家周一闭馆的美术馆，客户当场信任崩塌。

第 3 条是这个项目存在的理由：**正因为不能用「大概率对」的生成式产品糊弄，产品设计才有壁垒**。市面上 AI 行程 Demo 到处都是，没有一个敢把输出直接发给付了 30 万的客户。

### 3.2 我做的第一个判断：把「对」和「快」分开（1 分钟）

这个产品里有两类工作，我把它们从架构上彻底分开：

| | 谁来做 | 能不能错 |
| --- | --- | --- |
| **判断类**：这家酒店气质配不配这对夫妻 | 顾问 | 人的价值所在，产品不碰 |
| **组合类**：排顺序、选候选、写描述 | 模型 | 可以错，有校验层兜 |
| **事实类**：价格、容量、营业时间、汇率 | **规则引擎 + 数据库** | **绝不能错，所以不让模型碰** |

一句话：**模型做「选择题」，规则引擎做「计算题」，顾问做「判断题」。**

### 3.3 架构与四条链路（2 分钟）

四条链路，**每条都能独立降级**，一条挂了不让整个产品不可用（[总纲 §8](03-产品基建设计文档.md)）：

| 链路 | 做什么 | 挂了怎么办 |
| --- | --- | --- |
| L1 需求采集 | 客户原话 → 15 个槽位的结构化需求卡 | 模型失败 → 退回规则引导，顾问手填 |
| L2 检索 | 需求卡 → 候选池（硬过滤） | 候选 < 3 → **不硬生成**，返回可一键应用的放宽建议 |
| L3 生成校验 | 候选池 → 已校验行程（三道防线 + 自动重排） | `PLANNER_MODE=heuristic` 确定性编排器兜底 |
| L4 交付 | 方案 → 客户版 PDF / 长图（服务端剥离净价） | 导出失败仍可页面预览 |

两个我自己最满意的细节：

- **必问项不得静默假设**。忌口、无障碍、预算口径、是否含机票这 4 项缺任何一项，接口直接返回 409 拦住，不让生成。「客户没说忌口」≠「没有忌口」，这条写在代码里（`card.MUST_ASK`），不是写在提示词里。
- **商业优先级权重上限锁死 0.10**，配置成更高的值服务直接启动失败。这是产品决策，不是配置项——防的是以后有人想把「推自家高佣金资源」的权重悄悄调上去。

### 3.4 证据：我怎么证明它是对的（2 分钟）

质量保证分两层，**互不混用**——这是我认为最值得讲的方法论：

| 层 | 对象 | 方法 | 判定 |
| --- | --- | --- | --- |
| 单元/集成测试 | 确定性代码（约束、成本、权限、隐私） | pytest 断言 | 二值，必须 100% |
| **评测集** | 模型行为（抽取、编排） | 用例族 + 阈值 | **按族设门槛**，陷阱族必须 100% |

模型链路**不能靠单元测试保证**：同一输入两次结果可能不同，断言式测试要么过松等于没测，要么过紧天天误报。

结果（[评测 §6](10-评测标准与评测报告.md)、[数据分析 §2](08-数据分析报告.md)）：

- 真实模型 19/20 通过，规则层 15 通过 + **5 条标记为跳过**；
- 那 5 条跳过是抽取族用例——**dry-run 没跑模型，就不能给抽取族打勾**。很多评测体系的水分就出在这里；
- 上线门槛 G1–G5 全部达成，其中 G4（未确认不得生成）是接口层 409，G5（净价隔离）是服务端剥离，**都不是前端隐藏**。

唯一失败的用例是「老人生冷的少一点、走不了太多路」这种委婉表达没抽全。但风险等级我定的是 S3 不是 S2，因为**饮食和无障碍都在必问项里，模型漏了，规则会强制拦住追问**。这正是双层设计的价值：**模型漏了，规则兜住**。

### 3.5 这个项目做不到什么（1 分钟）⭐ 不要跳过

我在文档里明确列了拿不出来的东西（[数据分析 §8](08-数据分析报告.md)）：

| 缺什么 | 为什么缺 |
| --- | --- |
| 顾问修改率、工时节省实测 | **没有真实用户，没有手工基线** |
| 用户调研报告 | 没有真实访谈数据，**写了就是编** |
| 真实供应商数据 | M0 用的是 769 条合成数据 |
| Agent 需求文档 | **本项目根本没有动态 Agent**，只有两次固定模型调用，没有工具循环，没有自主决策 |

一句话总结：**M0 证明了「这套架构能不能做对」，还没证明「顾问愿不愿意用、能省多少」。前者是工程问题，已解决；后者是产品问题，需要真实用户，不是再写一个功能。**

### 3.6 下一步，以及一个反直觉的排序（1 分钟）

我的下一步优先级是：**① 找 2–3 名真实顾问测手工基线 → ② 实现前端埋点 → ③ 接一小批真实数据 → ④ M2 编辑能力 → ⑤ M1 语义检索。**

**把技术上最性感的语义检索排在最后**，理由是：向量检索解决的是「找得全」，而当前真正的瓶颈是「假设没验证」和「看不见用户行为」。硬过滤已经能满足 3 城场景。

**技术上更性感的事，不一定是当下最该做的事**——这是我在这个项目里最想表达的一条判断。

## 5. Q&A 预案（10 个大概率被问到的）

### Q1「这不就是套了个壳调 API 吗？」

不是。套壳的做法是：把需求丢给模型，让它连行程带价格一起吐出来。我的做法是**模型只输出 `resource_id`**，所有事实字段由服务端从数据库回填并二次比对。

产品的价值恰恰在模型之外：硬过滤、三道防线、7 条硬约束的三态判定、自动重排、成本规则引擎、净价隔离。**换一个模型，这套东西一行都不用改**——反过来说，如果换个模型产品就垮了，那才是套壳。

### Q2「20 条用例太少了吧？」

**对，这是这套评测最大的问题，我自己在[评测报告 §9](10-评测标准与评测报告.md) 里列了 6 条不足，第一条就是这个。**

更关键的不是数量少，是**用例来自构造而非真实询单**——构造用例的最大问题是，**你只会构造你已经想到的坑**。真实询单里的坑，往往是你没想到的那些。

所以我的下一步不是加功能，是把真实脱敏询单接进评测集，并把样本扩到每族 ≥ 10 条、补 Recall@K 标注、同用例跑 3 次看方差。

### Q3「硬约束零违反，是不是因为题目太简单？」

恰恰相反，这些坑是**用 Python 强制注入种子数据的**，不靠模型保证：只住 2 人的房型、不接 5 岁以下的旅馆、已过期的合约价、周一闭馆的博物馆、周二休业的餐厅、6 人 6 箱装不下的 5 座车。用例用 `must_not_contain_resources` 显式断言这些 ID 不得出现在最终方案里。

而且有 4 条用例**确实触发了重排**（说明模型第一轮真的踩了坑），只是都在 2 轮内收敛了。**零违反是校验层的功劳，不是模型天生不犯错**——这恰好证明校验层是必需的。

### Q4「24 秒是不是太慢了？」

对照基线来看不慢：顾问手工是小时级。而且 24 秒里有 19.5 秒是编排，输出 2,290 token 的完整 7 天行程。

真正要优化的是**等待体验不是绝对耗时**，所以我做了生成过程可视化。另外缓存命中率约 99%（13,312 / 13,432），说明 Prompt 模板化设计是有效的，这部分成本可以忽略。

### Q5「为什么不做 Agent？现在都在做 Agent。」

**因为这个项目不需要，硬做就是为了词而做。** 我的链路里模型只有两次固定调用（抽取、编排），没有工具调用循环，没有自主决策——这是一条确定性流水线，不是 Agent。

所以我在[文档索引](00-文档索引.md)里明确写了「Agent 需求文档 ⛔ 不写：本项目没有动态 Agent，不硬写」。

更进一步说：**这个场景恰恰不适合把决策权交给 Agent**。对客交付要求可复现、可追溯、可回归测试，而 Agent 的自主决策路径每次都不一样。如果未来要引入，我会放在「资源数据补全」这类内部任务上，不会放在对客生成链路上。

### Q6「没有真实用户，这个项目的价值怎么证明？」

**证明不了，我也没在文档里假装能证明。** [数据分析报告](08-数据分析报告.md) 开头第一句就是「尚未对客上线，没有任何线上流量」，第 8 节专门列了「这份报告拿不出来的东西」。

我能证明的是工程侧：架构能不能防住幻觉、约束能不能兜住、成本算不算得准。我不能证明的是业务侧：顾问愿不愿意用、到底省多少。

**把这两件事分清楚，而不是拿 95% 通过率去冒充业务成果**，是我做这个项目最在意的一条纪律。

### Q7「工时从 8 小时降到 2.5 小时，这个数据哪来的？」

**是假设，不是实测，文档里用加粗警告标了。**（[立项 §3](02-立项报告.md)：「本节全部是待验证的估算」）

而且我在立项报告里把它写成了**可证伪的假设 H1–H6**，每条都写了验证方法和「若不成立怎么办」。比如 H1（检索是最大工时占用项）若不成立，产品重心就要从检索移到编排辅助。

后来看行业资料还发现一个我原本没考虑到的点：**定制需求单的成单率最高约 10%**，意味着顾问九成的方案工时是沉没成本。如果属实，产品的收益口径就不是「单方案省 5.5 小时」，而是「让沉没的那九成变得更便宜」——这条我补进了验证清单作为 H6。

### Q8「一个人怎么做完前后端加文档的？」

AI 辅助开发，后端约 4,307 行、前端约 2,923 行、测试 112 项后端 + 12 个前端单测文件 + 1 套 Playwright E2E，测试与代码比约 1:2.4。

但我想强调的是**测试写在哪里**：几乎全部集中在规则层（约束、成本、权限、隐私）。**模型行为靠评测集验证，确定性逻辑靠单元测试验证，两者不混**——这是刻意的分工，不是写不动了。

### Q9「竞品都是大厂，你怎么打？」

**我不跟他们打同一场仗。**

- 携程飞猪的目标函数是**转化**，不是正确性，而且我的用户（定制社）的私域协议价**根本进不了 OTA 的库**——这是结构性的，不是他们做不到；
- 通用 AI 行程工具面向旅行者，错了用户自担；我面向顾问，错了是对客事故；
- 6 人游、无二之旅这类自营定制社**是客户不是对手**，他们公开的痛点数据反而佐证了我的前提。

护城河也不在模型，在**把散落资源结构化的运营能力**——这件事 AI 帮不了你，谁先做谁有壁垒。风险我也写了（[立项 §8 R1/R3](02-立项报告.md)）：数据冷启动质量不足、顾问不愿维护，对策是先窄后宽（先做 3 城）、把维护动作嵌进日常流程。

### Q10「如果重做一遍，你会改什么？」

三件事：

1. **先测基线再写代码**。我在立项报告 §7 里写了「立项后第一件事是测手工基线」，但实际执行时因为没有业务方配合，我跳过了它直接做了 M0。结果就是现在工程侧很扎实，业务侧一个数字都拿不出来。**这是我这个项目最大的方法论缺口，不是技术问题。**
2. **埋点和功能一起上**。F10-4 埋点被我排到了后面，导致现在即使有人用，我也看不见顾问改了什么。埋点表（[05](05-数据埋点表.md)）设计好了却没实现，这是典型的「先做能演示的」的短视。
3. **评测集从真实询单起步**。哪怕只有 5 条真实的，也比 20 条我自己构造的更有信息量。

## 7. 讲这个项目的三条自我提醒

1. **主动说缺口，不要等人问出来。** 「没有真实用户」这件事，我自己说出来是方法论意识，被问出来是翻车。
2. **区分工程数据和业务数据。** 95% 通过率是工程数据，工时节省是业务数据。混着讲一次，可信度全丢。
3. **讲判断，不要只讲功能。** 「为什么把 M1 语义检索排在最后」比「我做了语义检索」更有信息量。功能谁都能做，**排序才是产品能力**。

> 这套文档和这个项目真正想证明的一件事：**缺口写清楚，比补一份编出来的文档更可信。**
