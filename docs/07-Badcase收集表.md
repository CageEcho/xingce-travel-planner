## 1. 收集机制

| 环节 | 做法 |
| --- | --- |
| **来源** | ① 评测集跑测失败用例（自动）② 开发自测发现（人工）③ 顾问试用反馈（**待开通**）④ 线上埋点异常（**待埋点**） |
| **录入** | 每条一行，必填：现象、复现输入、期望、实际、归因、责任方 |
| **归因** | 四类：知识缺失 / 检索偏差 / 行程冲突 / 理解错误（见 §2） |
| **闭环铁律** | **任何修复必须附带一条新测试用例**，否则不算修完 |
| **节奏** | 每周跑一次全量回归 → 评审新增 Badcase → 定归因与责任人 → 下周验证修复 |

## 2. 四类归因

| 归因 | 典型表现 | 处置动作 | 责任方 |
| --- | --- | --- | --- |
| **知识缺失** | 库里没有该资源；关键字段为空导致硬过滤失效 | 生成补录工单 → 补数据 → 回归验证 | 运营 |
| **检索偏差** | 有合适资源但没召回；不合适的排在前面 | 调过滤条件/权重/embedding | 产品 + 算法 |
| **行程冲突** | 硬约束漏检、通勤不合理、休馆日踩坑 | 补约束规则或修数据字段 + 补用例 | 产品 + 研发 |
| **理解错误** | 槽位抽错、冲突未识别、追问答非所问 | 优化抽取 schema / 追问策略 / few-shot | 产品 |

> 💡 **预期分布**：知识缺失应占最大比例——这是 RAG 类产品的规律，前期瓶颈在数据不在模型。
> **实际分布见 §4**：当前样本以「理解错误」为主，因为 M0 用的是**自建合成数据，知识缺失被人为消除了**。这个偏差必须在接入真实数据后重新观测，不能拿现在的分布做结论。

## 5. 结论与下一步

1. **唯一的 S1 是设计缺陷不是代码 bug**：二值校验会让缺字段静默通过。这印证了 PRD-v2 风险 R2 的判断——**最危险的故障是「看起来正常」的那种**。
2. **BC-001 曾保留未修复，是有意识的决定**（10-25 复测时真实模型三轮均已通过）：委婉表达识别不全，但必问项兜底会强制追问，不会静默假设，**风险被降级为「多问一轮」而非「答错」**。修它要改 prompt 与 few-shot，收益不确定，排在真实数据接入之后。
3. **当前归因分布不可外推**：合成数据让「知识缺失」被人为压低。接入真实供应商数据后必须重跑分布，预期知识缺失会跃升为第一。
4. **最大缺口是没有真实用户的 Badcase**。目前全部来自自测与评测集，缺少「顾问觉得难用」这一类问题——那类问题恰恰只有真人会提。
5. **扩库本身会引入新 bug**（10-25 补充）：BC-013、BC-014、BC-018 都是资源量从 42 家扩到 300 家之后才出现的。单测在小数据上全部通过，只有用评测集在扩库后回归才暴露。结论：每次知识库规模或结构变化，都必须跑一次完整的真实模型评测。
